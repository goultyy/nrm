# NRM

A Windows desktop app for managing multiple remote Nginx servers over SSH, with an IIS Manager-style interface. Java 17+, JavaFX 21, Maven. There is no cloud component: profiles are stored locally and all certificate work happens on the server.

## Building and running

You need JDK 17 or newer and Maven 3.8+.

```
.\mvnw test            # run the unit tests
.\mvnw javafx:run      # start the app
.\mvnw package         # build target\dist (the jar and its libraries)
```

The profile store uses Windows DPAPI, so the app itself runs on Windows. The tests run on any OS because they use a passphrase-based key protector. The screen smoke tests are skipped where JavaFX can't start (no display).

### Windows installer

```
.\packaging\build-installer.ps1              # build, test, package
.\packaging\build-installer.ps1 -SkipTests
```

This runs `jpackage` on a JDK 17 or newer. It always produces a self-contained **app image** with its own trimmed Java runtime in `target\installer\NRM\` (about 100 MB; nothing else has to be installed, and the folder can be zipped and shared). If the **WiX Toolset 3.x** is installed (`winget install WiXToolset.WiXToolset`, then open a new terminal) it also produces an `.msi` and an `.exe` installer (per-user install, Start menu and desktop shortcuts, and an upgrade id so a newer version replaces an older one).

The icon is generated by `java tools\MakeIcon.java` (writes the PNGs in `src\main\resources` and `packaging\app.ico`).

## Where data lives

Profiles are saved to `%APPDATA%\NRM\profiles.nrm`. Start the JVM with `-Dnrm.dataDir=<folder>` to use a different folder (for a portable install or testing).

Alongside the store you may see `profiles.nrm.bak` (the previous version, kept on every save) and `profiles.nrm.damaged-<timestamp>` (a file the app couldn't read and moved aside instead of overwriting).

`logs\app.log` (Help > Open application log) records unexpected errors and a short trail of what was done to which server. It never contains passwords or file contents, and rotates at 1 MB. The exact commands sent to a server are in the command log panel instead. `window.properties` remembers the window's position and size. `settings.properties` remembers the colour theme.

Colours: View > Theme chooses System (follows the Windows "app mode" setting, including when it changes while NRM is open), Light or Dark. Dark is one stylesheet, `mt/su/nrm/ui/dark.css`, loaded on top of JavaFX's standard theme; light is that stylesheet not being loaded. Colours set directly in the code (the red of an error message, the grey of a hint, the retro pictures on the tiles) are not themed yet.

Keyboard: F5 refreshes from the server, Ctrl+K connects, Ctrl+Shift+K disconnects, Ctrl+M shows the server list, Ctrl+L toggles the command log, Ctrl+Q exits.

## How profiles are protected

Each save generates a fresh random AES-256 key and encrypts all profiles with AES-GCM. That key is then wrapped with Windows DPAPI, which ties it to your Windows user account, so no master password is needed and the file is useless on another account or machine. The file header is authenticated along with the data, so any modification is detected on load.

Writes go to a temp file, are flushed to disk, and then atomically replace the old file, so a crash mid-save can't leave a half-written store. Secrets are masked in every `toString()`, and passwords may be left empty to be asked for when connecting.

If the store can't be opened, `ProfileStoreException.kind()` says why: `CANNOT_UNLOCK` (different Windows user or machine), `DAMAGED` (a backup may be restorable via `ProfileRepository.recoverFromBackup`), `UNSUPPORTED_VERSION` (saved by a newer app), `PROTECTOR_MISMATCH`, or `IO`.

### Profile model

A `ServerProfile` holds the connection (host, port, username, password or private key), how to gain root (`NONE`, `SUDO_PASSWORD`, or `SUDO_NOPASSWD`; a null sudo password means "reuse the login password"), a pinned host key fingerprint, an optional SSH gateway (jump host: its own host, port, user, password or private key, and its own pinned host key; the server is reached through a direct-tcpip channel opened on it, so the gateway's key is checked before anything is sent to it and the server's key is checked as usual), the `ServerPaths` section, and cached server facts: the detected `ConfigLayout` and the openssl and certbot `ToolStatus` (null until first checked).

`ServerPaths` defaults: nginx `/usr/sbin/nginx`, config `/etc/nginx`, certbot `/usr/bin/certbot`, Let's Encrypt `/etc/letsencrypt`, CA storage `/etc/nrm/ca`, manual certs `/etc/nginx/ssl`, temp `/tmp`. All must be absolute and free of control characters, since they end up in remote commands.

`ProfileRepository` is what the UI talks to. It validates, requires unique names (ignoring case), stamps created and updated times, and writes to disk before changing anything in memory, so a failed save leaves no half-applied state. It hands out copies, so editors can change a profile freely until they call `update`.

## Editing nginx configuration

The app never edits a file on the server directly. A connected server's config is read once (the main `nginx.conf` plus everything it includes) into memory, parsed losslessly, and edited there. Changes sit under **Pending Changes** until you apply them:

1. **Local checks**: syntax, and the virtual host rules (ports, paths, required SSL files, and so on).
2. **Server test**: the changed files are uploaded to temporary files, a scratch copy of the config folder is built with them in place, and `nginx -t` runs on that copy. The live config is not touched.
3. **Review**: a diff of every file that will change, and the test result. Nothing happens until you confirm.
4. **Apply**: previous files are backed up under `/var/backups/nrm/<timestamp>` on the server, the new files are written, `nginx -t` runs on the live config, and only then is nginx reloaded. If that test fails, the backups are restored before anything reloads.

The parser keeps whitespace, comments and any directive it does not understand exactly as they were, so regenerating an unchanged file gives back identical bytes (checked against real configs and 400 randomly generated ones). Lua blocks and other non-nginx bodies are kept as opaque text. Files outside the nginx config folder, and files that are not valid UTF-8 or do not parse, are shown but never edited.

## Testing against a real server

Most tests run offline. Tests that need a real server are skipped unless these environment variables are set (use a disposable machine, never production):

```
NRM_TEST_HOST, NRM_TEST_USER, NRM_TEST_PASSWORD, NRM_TEST_PORT (default 22)
```

The user needs `sudo` (with a password) and nginx must be installed. The full cycle test creates, applies, breaks, rolls back and deletes a virtual host, and leaves the server as it found it.

The Cloudflare tests against the real API are skipped unless `NRM_TEST_CF_TOKEN` is set. They are read-only unless `NRM_TEST_CF_WRITE=1` is also set, and the write tests need `NRM_TEST_CF_ZONE` (a zone name), `NRM_TEST_CF_TUNNEL` (a tunnel name) and `NRM_TEST_CF_PREFIX` (a name under that zone, such as `test.example.com`). They create one throwaway `nrm-test-...` DNS record and one throwaway tunnel route, then remove them and check the tunnel's original rules are unchanged. Pass the token as an environment variable only; never write it to a file.

## Beyond virtual hosts

Under a connected server the tree also has:

- **Load Balancing**: `upstream` groups, created and edited with a wizard: name and how to share traffic (evenly, least busy server, same visitor to the same server, by a key such as the URL, random), then the servers as rows (address, port, weight, active/backup/down, failures allowed and retry time), then connection reuse, then a review of the exact block. A location's "Forward to" offers your groups.
- **Cache Zones**: `proxy_cache_path` zones, created with a wizard: name and folder, disk size and index memory (with an estimate of how many items fit), how long unused items are kept, and layout options. Sizes and times are entered as numbers with units. The apply step creates the folder above a cache path if it is missing, because nginx creates only the last level itself, and makes sure every cache folder is owned by nginx's worker user (`nginx -t` run as root would otherwise leave it root-owned, and the workers then fail with "opendir() failed (13: Permission denied)").
- **Cache statistics** (optional, under the Cache Zones table): off until you turn it on. Turning it on adds, as ordinary pending changes, a `log_format nrm_cache` with `$upstream_cache_status`, a `map` that keeps non-cached requests out, and an extra `access_log /var/log/nginx/nrm-cache.log` in the http block and beside every site or location that has its own `access_log` (existing logs are untouched; `access_log off` blocks are left alone). The pane then counts HIT, MISS, EXPIRED, STALE, BYPASS and the rest per site from the end of that log, with a hit ratio. Turning it off removes exactly what was added.
- **Cloudflare** (optional, needs an API token saved under "Cloudflare" in the server's settings): a page with two icons, **DNS Zones** and **Tunnels**. Each opens a page of tiles, one for every zone or tunnel the token can see, and those zones and tunnels are also listed under the entry in the tree, as sites are under Virtual Hosts. "New DNS zone" and "New tunnel" on those pages add a domain or create a tunnel; unlike everything else these happen on Cloudflare at once (they can't be staged, since later changes depend on them existing), after a dialog that says so. A new zone stays pending until the domain's nameservers are changed at its registrar, which the app shows right after; a new tunnel's run token is shown once, in the install command, and is kept out of the command log. A zone's page lists its DNS records; a tunnel's page lists the applications it publishes, and "Publish application" there adds a route plus its proxied CNAME (in the zone you pick) in one step. The token needs **Zone: Read**, **DNS: Edit** and **Cloudflare Tunnel: Edit**, limited to the zones and account you manage here. A virtual host can be added to Cloudflare from its right-click menu or the Actions pane ("Add to Cloudflare"): a wizard asks whether to create a DNS record or a tunnel endpoint, then suggests the server's own IP addresses (public ones first for a DNS record) and the ports nginx listens on, read from the server through the command log, along with the ports in the site's `listen` lines; it ends with a review and stages the result. Edits are only staged (bold rows, a count in the tree) until you "Review and apply": before anything is sent, everything it will touch is read again, and if it changed on Cloudflare in the meantime nothing is sent. Order when applying: DNS deletions, then tunnel routes, then DNS additions and changes, so a hostname never points at a route that doesn't exist yet. Every request is written to the command log with the token masked. Tunnel routes can't be edited for a tunnel configured by a file on the server (Cloudflare ignores the API there). The staged changes are separate from the nginx pending changes, which are about files on the server.
- **Download a certificate and its chain** (Certificates and Authority > Certificates tabs, "Download"): saves a server certificate as a Windows `.p7b` (every certificate, installable), a PEM bundle, the certificate alone, or the chain alone. Only certificate blocks leave the server (a key sharing the file is cut out there), and the chain is completed by following the issuer through the server's own authorities. A CA itself is downloaded from the Authority tab.
- **File Explorer** (formerly File Transfer): this computer on the left, the server on the right, with upload, download, rename, delete and a plain text editor. Double-click a file (or Edit) to open it; Save (Ctrl+S) writes it back over the same logged SFTP session, as the login user, so root-owned files can't be saved. Files over 2 MB, binary files and files that are not UTF-8 are refused rather than risked.
- **Log Formats**: your own `log_format` definitions, made with an interactive builder. Pick fields from a searchable list (grouped: client, time, request, response, upstream, connection), arrange them as rows with your own punctuation, or switch to JSON, where each field becomes a key (numbers unquoted) and values are escaped for JSON. Start from a preset (standard, with timings, behind a proxy, with cache result, minimal, JSON) or read any existing format back into rows. A sample line updates as you build, and the last page shows the exact directive. New formats are placed before anything that could use them, as nginx requires. A format that an `access_log` still uses can't be deleted, and a site's Logging tab offers `combined` plus every format defined on the server.
- **Change History**: every apply keeps the files it replaced in `/var/backups/nrm/<time>-<id>/`, with a `manifest` of what it touched (created, changed, deleted, and any enabling symlinks). The Change History screen lists those applies, newest first. "Show differences" previews, and "Restore before this change" builds the changes that undo it and sends them through the normal pipeline: local checks, `nginx -t` on a scratch copy, a diff to confirm, and automatic rollback if nginx rejects the result. Restoring is refused while changes are pending. A backup is only listed once the new config passed `nginx -t`, and applies made before this feature existed have no manifest and are not listed. Backups are never pruned automatically; "Delete backup" removes one.
- **Security headers**: on a site's Headers tab, "Security headers" adds browser protections from a guided list: Basic (nosniff, X-Frame-Options, Referrer-Policy), Recommended (plus HSTS and Permissions-Policy) and Strict (plus Content-Security-Policy and cross-origin isolation), or ticked one by one with editable values. Each shows what it protects against, what it can break, and what the site has now. Headers are added with `always`, replace same-named ones in place, and leave other headers alone. It warns that nginx ignores a site's `add_header` lines inside any location that has its own (and names those locations), that HSTS means nothing without HTTPS, and about `preload`.
- **Log analysis**: on the Logs page, "Analysis" turns the lines read into totals, failure rate, traffic over time, busiest pages and visitors, pages with errors, browsers and crawlers, slowest and largest responses, and status codes. "Read as" chooses Automatic (standard format, JSON lines, and `rt=` timings) or any format defined under Log Formats; the search box limits what is analysed, and double-clicking a page or visitor shows its lines. Request times need a format that logs them (the "with timings" preset).
- **Rate Limits**: request-rate and connection limit zones, created with a wizard: what to limit, who is counted (each visitor, whole site, each URL, ...), then the allowed rate and zone size. A location's Limits tab lists your zones with an "Add request limit" (burst, no-delay) and "Add connection limit" builder, and its Caching tab has zone and "keep fresh for" builders. The editor warns when a location uses a zone that isn't defined.
- **Global Settings**: workers, logging, HTTP and TLS defaults and compression defaults from the main `nginx.conf`, with the detected layout shown.
- Per location (in the virtual host editor): static files, reverse proxy, redirect, login (`auth_basic`), allow/deny rules, request and connection limits, gzip, caching and error pages. New http-level objects are added to the `http` block of the main `nginx.conf`, which is edited through the same pending-changes pipeline as everything else.

## Add-ons

Optional features live under **View > Features**. All are off until you turn them on; each one you turn on gets its own entry under every connected server and a tile in an "Add-ons" group on the server overview. An add-on changes a server's configuration only through the pending changes (you review, then apply), and anything it runs on the server shows in the command log. More add-ons can be supplied from outside by registering a `mt.su.nrm.ui.Feature` in `META-INF/services` (found with Java's `ServiceLoader`).

- **Status page**: live figures from nginx's `stub_status`: connections now, requests and accepted connections per second, what open connections are doing (reading, writing, waiting), dropped connections, and a chart of the last minutes. Turning it on adds a small `server` that listens on `127.0.0.1` only (port chosen from ports not in use), so it can't be reached from outside and doesn't touch your sites; turning it off removes exactly that. A `stub_status` you set up by hand is found and shown, never changed, and flagged if nothing limits who can read it. Readings are taken by running `curl` (or `wget`) on the server, only while the page is open, every 2, 5, 10 or 30 seconds, and stop after three failures in a row so they can't flood the command log. The numbers are for the whole nginx; stub_status has no per-site figures, response codes or bandwidth. Needs nginx built with `--with-http_stub_status_module`, which the page checks.
- **Real IP** (per site): for sites behind a proxy. Without it nginx logs and rate-limits the proxy's address for every visitor. Each virtual host has a Real IP part (under Security) that writes `set_real_ip_from`, `real_ip_header` and `real_ip_recursive` in that site's own server block, so different sites can sit behind different proxies; settings already there, made by hand, are shown and are left exactly as they are unless you change them. It starts from a preset for the kind of proxy: Cloudflare's proxy (trusts Cloudflare's published ranges, read from Cloudflare when you ask, and reads `CF-Connecting-IP`), a Cloudflare Tunnel (trusts only this machine), another proxy on this server, a load balancer on a private network, or something else where you choose the header and addresses. Presets are data, and more can be added by providing a `mt.su.nrm.proxy.ProxyPresetProvider`. nginx reads one header per site, so each site names one kind of proxy; several proxies in one chain can share `X-Forwarded-For` with the look-past-trusted option. Settings at the http level, if any, are shown and are replaced for a site that sets its own. Only the addresses you list are believed, since trusting too much lets anyone fake their address: trusting everything (`/0`) is refused and very wide public ranges are warned about. Every address that goes into the configuration is checked first, including those read from Cloudflare. Needs nginx built with `--with-http_realip_module`; if it lacks it, `nginx -t` rejects the change and nothing is applied.

## SSL certificates

The **SSL Certificates** node has two tabs. Every view shows the same certificate list, read from the server once (Refresh re-reads it). Certificates are read with `openssl x509` only; private keys are never opened, downloaded or shown. Selecting a certificate shows its details: subject (common name, organisation, unit, country, state, city, e-mail), all subject alternative names, issuer, validity, serial, public key, signature algorithm and fingerprint. Expired and soon-to-expire (30 days) certificates are highlighted.

**Certificates** lists everything found in the places nginx uses: files named by `ssl_certificate`, the Let's Encrypt folder, the manual certificate folder, and the CA.

- **Let's Encrypt** runs `certbot certonly` on the server: the webroot challenge by default, or the nginx plugin, with a contact e-mail and an optional certificate name. There is no DNS challenge in this version, so wildcard names are refused. A staging option is there for testing. **Renew** runs `certbot renew` and reloads nginx.
- **Use in virtual host** sets a certificate on a site as a pending change (adding `listen 443 ssl` if needed).

**Certificate Authority** has its own sub-tabs:

- **Authority**: any number of private root CAs per server (for example one per team or environment; no intermediates), each in its own folder under the CA folder with its key readable only by root. A CA created by an earlier version directly in the CA folder is still found. Creating one asks for its identity (common name, organisation, unit, country, state, city, e-mail), the key type (RSA 2048/4096 or ECDSA P-256/P-384) and validity. The list shows each CA with its expiry and how many certificates it has issued. Only a CA's public certificate can be downloaded, to install on the machines that should trust it.
- **Certificates**: choose one of the CAs to see what it has issued, and **Issue certificate** from it, which asks for the same identity details plus:
  - **Names (SAN)**: DNS names (wildcards allowed), IP addresses, `email:me@example.com` and `uri:https://example.com/path`. For a server certificate the common name is added as a DNS name or address automatically, because modern clients ignore the CN.
  - **Used for**: server, client (people and devices logging in), or both (extended key usage).
  - Key type, validity and an optional file name (so two CAs can each issue a certificate for the same name). Client certificates need no host names.
  
  Certificates go into the manual certificate folder; the key is created there with mode 600 and the finished certificate is verified against the CA before it is kept.

All values are checked before anything is sent, and are limited to plain characters so they can be written safely into openssl's configuration. Everything runs through the same logged SSH layer, so the exact commands are visible in the command log.

## The server overview

Clicking a server in the tree shows its facts and, once connected, its virtual hosts as tiles: a small picture of a web page for each site with its name, bindings and content underneath, wrapping into rows as wide as the window. The picture is a retro grey desktop window that shows what the site does (navy title bar and text lines: serves files, purple with two boxes and an arrow: proxies to another server, orange with a big arrow: redirects, grey: other); a yellow padlock means HTTPS, and a small yellow (changed) or blue (new) square marks a site with changes that haven't been applied. Double-click a tile to open the site inside the window: its parts (General, Locations, SSL, Headers, Limits, Rewrites, Error pages, Logging) appear as retro icons grouped by category, and clicking one loads it. Add and delete virtual hosts from the Actions pane.
